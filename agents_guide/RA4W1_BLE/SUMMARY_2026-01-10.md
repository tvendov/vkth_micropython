## The Missing Piece: GATT Database

### What is GATT DB?
GATT Database defines all BLE services and characteristics that the device exposes.
It's a **static configuration** that must be set BEFORE advertising starts.

### Why It's Missing
The current implementation initializes the BLE stack but never calls:
```c
R_BLE_GATTS_SetDbInst(&gatt_db_config);
```

### Consequence
- ✅ Device can advertise
- ✅ Device can connect
- ❌ Device has NO services to offer
- ❌ BLE scanner sees empty device

## Solution: Three Approaches

### 1. Static GATT DB (Recommended)
Use Renesas QE tool to generate GATT DB configuration.
- **Pros:** Optimized, production-ready, full feature support
- **Cons:** Requires QE tool, less flexible
- **Effort:** 1-2 days

### 2. Dynamic GATT DB (Flexible)
Implement MicroPython `gatts_register_services()` wrapper.
- **Pros:** Flexible, matches standard MicroPython API
- **Cons:** More complex, runtime overhead
- **Effort:** 1-2 weeks

### 3. Hybrid (Best of Both)
Static base services + dynamic extensions.
- **Pros:** Balanced approach
- **Cons:** Complex handle management
- **Effort:** 2-3 weeks

## Key Technical Insights

### GATT DB Structure
```c
st_ble_gatts_db_cfg_t {
    p_uuid_table[]        // Packed UUID bytes
    p_attr_cfg[]          // Attribute definitions
    p_uuid_cfg[]          // UUID index
    p_attr_val_table[]    // Attribute values
}
```

### Critical Relationships
1. **uuid_offset** in attr_cfg → points to UUID in uuid_table
2. **first/last** in uuid_cfg → handle range for each UUID
3. **next** in attr_cfg → linked list of attrs with same UUID
4. **p_data_offset** → points to value in attr_val_table

### Validation Rules
- All offsets must be valid
- Handle chains must be consistent
- No overlapping data regions
- Handles must be sequential (0, 1, 2, ...)
