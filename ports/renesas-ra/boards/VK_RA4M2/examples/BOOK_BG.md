# Книга: MicroPython за VK_RA4M2 чрез демонстрационни примери

## Цел

Тази книга е направена върху реално наличния пакет от примерни `.py` файла за `VK_RA4M2`.

Тук целта не е само да се изброят файловете.

Целта е да се покрият всички глави, теми и примери от плана, без пропуски и без измислени ресурси.

Затова книгата е организирана в три слоя:

1. Ресурсна карта на борда и порта.
2. Матрица за пълност спрямо учебния план.
3. Подробни глави с кодови откъси и препратки към всички реални сорс файлове.

## Как да се ползва книгата

Книгата се чете заедно със сорс файловете в `examples`.

Препоръчителният ритъм е:

1. Прочитате теорията в съответната глава.
2. Стартирате показания минипример.
3. Отваряте пълния `.py` файл.
4. Преглеждате ресурсния header в началото му.
5. Променяте само по една стойност и наблюдавате ефекта.

Когато примерът съдържа предпазен флаг като `DO_WRITE`, `DO_BOOTLOADER`, `DO_LIGHTSLEEP`, `DO_DEEPSLEEP` или `SET_DEMO_TIME`, започвайте с безопасната стойност.

## Ресурсна карта на VK_RA4M2

Книгата и примерите приемат следната карта на ресурси:

- LED: `1 брой` -> `LED1 = P204`
- Бутон: `1 брой` -> `SW1 = P400`
- USB device пинове: `USBDP = P914`, `USBDM = P915`, `USB_VBUS = P407`
- ADC външни входове: `13 броя` -> `P000`, `P001`, `P002`, `P003`, `P004`, `P005`, `P006`, `P007`, `P008`, `P013`, `P014`, `P015`, `P500`
- ADC вътрешни източници: `3 броя` -> `ADC.CORE_TEMP`, `ADC.CORE_VREF`, `ADC.VREF`
- DAC изходи: `2 броя` -> `P014`, `P015`
- PWM изходи: `14 броя` -> `P107`, `P106`, `P105`, `P104`, `P113`, `P114`, `P112`, `P115`, `P608`, `P409`, `P408`, `P600`, `P304`, `P303`
- UART: `4 инстанции` -> `UART(0)`, `UART(2)`, `UART(7)`, `UART(9)`
- I2C master: `2 инстанции` -> `I2C(0)=P400/P401`, `I2C(1)=P100/P101`
- I2CTarget: `2 инстанции` -> `I2CTarget(0)=P400/P401`, `I2CTarget(1)=P100/P101`
- SPI: `1 канал` -> `CS=P103`, `SCK=P102`, `MISO=P100`, `MOSI=P101`
- SoftI2C: наличен
- SoftSPI: наличен
- TouchPad входове: `12 броя` -> `P205`, `P206`, `P407`, `P408`, `P409`, `P410`, `P411`, `P412`, `P413`, `P414`, `P415`, `P708`
- CTSU специален пин: `P207 = TSCAP`
- Хардуерни таймери: `6 броя` -> `Timer(1)`, `Timer(2)`, `Timer(3)`, `Timer(4)`, `Timer(5)`, `Timer(6)`
- Софтуерен таймер: `Timer(-1)`
- RTC: `1 брой`
- Вътрешна файлова система: `/flash`
- `renesas.Flash`: наличен block device
- `dataflash`: `8 KB`

Важни уточнения:

- `SPI` тук се разглежда като `1` канал.
- `Timer(-1)` тук се разглежда като софтуерен таймер.
- `SW1` е върху `P400`, което влиза в конфликт с `I2C(0).SCL`.
- `LED1` е active-low: логическа `0` го светва, логическа `1` го гаси.
- `Pin.PULL_UP` се ползва в курса; `Pin.PULL_DOWN` не се разглежда като наличен ресурс в тези уроци.
- `lightsleep` и `deepsleep` са показани предпазливо.

## Част I: Първи стъпки с борда и с MicroPython

### Глава 1. Първа програма

Първата програма трябва да даде веднага видим резултат и да покаже как изглежда MicroPython файл за `VK_RA4M2`.

Ключова идея:

```python
from machine import Pin  # Импортираме класа Pin, чрез който управляваме GPIO пиновете.
import time  # Импортираме модула time, за да правим закъснения между действията.

led = Pin("LED1", Pin.OUT, value=1)  # Създаваме изходен обект за LED1 и започваме с изгасен LED.

for blink_index in range(3):  # Обхождаме три последователни мигания с for цикъл.
    led.value(0)  # Светваме LED1 като подадем активното за платката ниво.
    time.sleep_ms(300)  # Изчакваме 300 милисекунди, за да се вижда светването.
    led.value(1)  # Гасим LED1, за да завършим едно мигане.
    time.sleep_ms(300)  # Изчакваме още 300 милисекунди преди следващото мигане.
```

Тук се виждат наведнъж:

- `Pin`
- `for`
- `sleep_ms`
- active-low поведението на `LED1`

### Глава 2. Първи асинхронни примери

Преди да влезем в детайлите на езика, полезно е да се види как изглежда неблокиращото мислене.

Минипример:

```python
import asyncio  # Импортираме asyncio, за да правим неблокиращи задачи в MicroPython.
from machine import Pin  # Импортираме класа Pin, за да управляваме LED1 като цифров изход.

led = Pin("LED1", Pin.OUT, value=1)  # Създаваме изход за LED1 и започваме от изгасено състояние.

async def blink_task():  # Дефинираме асинхронна задача, която ще мига без да блокира event loop-а.
    while True:  # Повтаряме мигането безкрайно.
        led.value(0)  # Светваме LED1.
        await asyncio.sleep_ms(500)  # Отстъпваме управлението за 500 ms.
        led.value(1)  # Гасим LED1.
        await asyncio.sleep_ms(500)  # Отново отстъпваме управлението за 500 ms.
```

Втори минипример:

```python
async def count_seconds_task():  # Създаваме втора задача, която брои секундите.
    seconds = 0  # Началната стойност на брояча е нула секунди.
    while True:  # Повтаряме и тази задача безкрайно.
        seconds += 1  # Увеличаваме брояча с една секунда.
        print("Изминали секунди:", seconds)  # Показваме колко време е минало от старта.
        await asyncio.sleep(1)  # Чакаме точно една секунда без блокиране на event loop-а.
```

Тези примери показват две идеи:

- `asyncio` като кооперативен scheduler
- разделяне на поведението на независими задачи

- `examples/01_blink_async.py`
- `examples/02_two_tasks.py`

### Глава 4. Оператори, условия и цикли

Тази глава покрива аритметика, сравнения, логика и контрол на потока.

Пример:

```python
left_value = 7  # Първата числова променлива участва в аритметичните операции.
right_value = 3  # Втората числова променлива е вторият операнд.

sum_value = left_value + right_value  # Събираме двете стойности с оператора плюс.
logic_result = (left_value > right_value) and (left_value != right_value)  # Комбинираме логически оператори.

if left_value < right_value:  # Проверяваме първото условие.
    print("По-малка")  # Този ред би се изпълнил, ако първото условие е вярно.
elif left_value == right_value:  # Ако първото условие е невярно, проверяваме второто.
    print("Равна")  # Този ред би се изпълнил при равенство.
else:  # Ако нито едно от горните условия не е изпълнено, влизаме в else клона.
    print("По-голяма")  # Тук попадаме с текущите примерни стойности.
```

Циклите са показани и в трите практически форми:

```python
for index in range(3):  # Изпълняваме цикъл точно три пъти.
    print(index)  # Печатаме текущата стойност на брояча.

counter = 0  # Създаваме брояч за while цикъла.
while counter < 3:  # Повтаряме докато броячът е по-малък от три.
    print(counter)  # Печатаме текущата стойност на брояча.
    counter += 1  # Увеличаваме брояча, за да не останем в безкраен цикъл.

attempt = 0  # Създаваме брояч за демонстрацията.
while True:  # Влизаме в безкраен цикъл, който ще прекъснем с break.
    print(attempt)  # Печатаме текущата стойност, като това винаги се случва поне веднъж.
    attempt += 1  # Увеличаваме брояча след изпълнението на тялото.
    if attempt >= 2:  # Проверяваме условието за прекратяване след тялото на цикъла.
        break  # Напускаме цикъла, което прави конструкцията еквивалент на do-while.
```

Важни уточнения за начинаещи:

- `goto` няма в Python и в MicroPython
- `switch-case` няма в класическия MicroPython синтаксис на тези примери
- еквивалентите са `if/elif/else`, таблици, `break`, `continue`, `return`
- `do-while` се показва като `while True` + `break`

### Глава 12. Аналогов вход и ADC

Пример:

```python
from machine import ADC  # Импортираме класа ADC, чрез който се четат аналоговите канали.

temperature_adc = ADC(ADC.CORE_TEMP)  # Създаваме ADC обект за вътрешния температурен канал.
vref_adc = ADC(ADC.CORE_VREF)  # Създаваме ADC обект за вътрешното опорно напрежение.

print(temperature_adc.read())  # Четем суровата ADC стойност на вътрешния температурен канал.
print(vref_adc.read())  # Четем суровата ADC стойност на вътрешното опорно напрежение.
```

Тук се учат:

- какво е ADC
- как напрежението става число
- разликата между сурово четене и `read_u16()`
- защо вътрешните канали са добър старт

Важно уточнение за `RA4M2`:

- Този MCU е с `ADC12`, тоест хардуерната резолюция тук е `12 bit`, а поддържаните режими са `12 / 10 / 8 bit`.
- В текущия порт може да се избира режим още при създаване на обекта: `ADC(pin_or_channel, bits=8)`, `ADC(..., bits=10)`, `ADC(..., bits=12)`.
- Настройката за `bits` е глобална за ADC периферията, а не отделна за всеки ADC обект.

Кратък пример:

```python
from machine import ADC  # Импортираме ADC за избор на резолюция при създаване на обекта.

adc_fast = ADC("P000", bits=8)  # Създаваме ADC обект с 8-битова резолюция за бързо четене.
adc_balanced = ADC("P001", bits=10)  # Създаваме ADC обект с 10-битова резолюция за баланс бързина/точност.
adc_precise = ADC("P002", bits=12)  # Създаваме ADC обект с 12-битова резолюция за максимална точност.

print(adc_fast.read(), adc_balanced.read(), adc_precise.read())  # Четем и трите канала и показваме резултатите.
```

Практическа бележка за времето на преобразуване при текущите тактове на `VK_RA4M2`:

- при минимално валидно семплиране и `ADCLK = 50 MHz` самото A/D преобразуване е приблизително `0.31 us` за `8 bit`, `0.35 us` за `10 bit`, `0.39 us` за `12 bit`
- при по-дълго семплиране, например около reset/default настройката на `ADSSTR`, стойностите са приблизително `0.41 us`, `0.45 us`, `0.49 us`
- това е време на хардуерния ADC, а не пълното време на извикването `ADC.read()` от Python
- ако искате да мерите целия път през MicroPython, използвайте `time.ticks_us()` около самото извикване
- за практическо измерване на пълното време на `ADC.read()` виж `examples/23_timing/07_adc_timing_measure.py`, където се мери последователно в `8 / 10 / 12 bit`

Наличните външни ADC пинове в този курс са:

`P000`, `P001`, `P002`, `P003`, `P004`, `P005`, `P006`, `P007`, `P008`, `P013`, `P014`, `P015`, `P500`

```python
import time  # Импортираме time за блокиращото закъснение.

```

Хардуерен таймер:

```python
from machine import Timer  # Импортираме Timer за хардуерния таймер.

timer = Timer(1)  # Използваме един от наличните хардуерни machine.Timer канали от Timer(1) до Timer(6).
timer.init(freq=4, callback=timer_callback, hard=False)  # Стартираме Timer(1) на 4 Hz с callback извън hard IRQ контекст.
```

Софтуерен таймер:

```python
from machine import Pin, Timer  # Импортираме Pin и Timer за демонстрацията на софтуерния таймер.
import time  # Импортираме time, за да оставим таймера да работи кратко време.

led = Pin("LED1", Pin.OUT)  # Вземаме LED1 като видим индикатор за сработване на callback-а.
soft_timer = Timer(-1)  # Създаваме софтуерен таймер чрез идентификатор -1.
soft_state = {"count": 0}  # Пазим броя сработвания в mutable структура.
started = False  # С този флаг ще следим дали таймерът е стартирал успешно.

def soft_timer_callback(timer_object):  # Това е функцията, която ще се извиква при всяко сработване на софтуерния таймер.
    soft_state["count"] = soft_state["count"] + 1  # Увеличаваме брояча при всяко събитие.
    led.value(0 if led.value() else 1)  # Превключваме LED, за да виждаме че callback-ът се изпълнява.

if not started:  # Ако още не сме стартирали таймера, пробваме втория стил с честота.
    try:  # Влизаме в защитен блок за втория опит.
        soft_timer.init(freq=4, callback=soft_timer_callback, hard=False)  # Пробваме инициализация с честота 4 Hz.
        started = True  # Отбелязваме, че вторият стил е успял.
        print("Timer(-1) тръгна с freq API.")  # Печатаме кой резервен стил е сработил.
    except Exception as second_error:  # Ако и вторият стил не тръгне, само информираме потребителя.
        print("freq API също не тръгна:", second_error)  # Показваме причината и за втория неуспех.
```

Тук трябва да остане ясно:

- `Timer(1)` до `Timer(6)` са хардуерни
- `Timer(-1)` е софтуерен
- `asyncio` е още една неблокираща алтернатива

Практическа бележка за `time.ticks_us()`:

- ползвайте `time.ticks_us()` и `time.ticks_diff()` за относителни интервали в микросекунди
- в този порт `time.ticks_us()` идва от хардуерно поддържан `mp_hal_ticks_us()`, а не от измислен Python брояч
- това е много полезно за сравнение на latency и `ADC.read()` време, но не е заместител на осцилоскоп при хардуерна прецизност

#### Подглава 14.1. Хардуерни таймери

След базовата идея за `Timer(1)` и `Timer(-1)` е важно да се види какво реално може хардуерният таймер на този порт.

В текущия firmware за `VK_RA4M2`:

- `Timer(1)` до `Timer(6)` са хардуерни AGT таймери
- `Timer(-1)` е софтуерен таймер върху системния tick
- хардуерните таймери поддържат `Timer.PERIODIC` и `Timer.ONE_SHOT`
- налични са `freq()`, `period()` и `counter()`
- налични са `output compare`, `input capture` и `event count`
- при `event count` няма channel callback; ако искате callback на всеки `N` импулса, ползвате базовия `Timer.callback()` и задавате `period=N`

Базов пример за periodic и one-shot:

```python
from machine import Timer  # Импортираме Timer, за да използваме хардуерните таймери.

periodic_timer = Timer(1)  # Вземаме Timer(1) за периодичен режим.
oneshot_timer = Timer(2)  # Вземаме Timer(2) за еднократен режим.

periodic_timer.init(mode=Timer.PERIODIC, freq=2, callback=periodic_callback, hard=False)  # Пускаме периодичен таймер на 2 Hz.
print(periodic_timer.period())  # Показваме периода в сурови AGT counts.
print(periodic_timer.counter())  # Показваме текущия суров counter.

oneshot_timer.init(mode=Timer.ONE_SHOT, freq=2, callback=oneshot_callback, hard=False)  # Пускаме еднократен таймер със същия базов период.
```

Това се вижда подробно в:

- `examples/23_timing/13_hardware_timer_periodic_oneshot.py`

Пример за output compare callback:

```python
from machine import Timer  # Импортираме Timer, защото output compare работи през хардуерния таймер.

timer = Timer(1)  # Използваме Timer(1) като базов таймер за compare събитията.
timer.init(mode=Timer.PERIODIC, freq=10, callback=cycle_callback, hard=False)  # Пускаме бавен периодичен таймер на 10 Hz.

period_counts = timer.period()  # Вземаме периода в сурови counts.
channel_a = timer.channel(1, mode=Timer.OC, compare=period_counts // 4, callback=compare_a_callback)  # Настройваме compare A на 1/4 от периода.
channel_b = timer.channel(2, mode=Timer.OC, compare=(period_counts * 3) // 4, callback=compare_b_callback)  # Настройваме compare B на 3/4 от периода.
```

Това се вижда подробно в:

Пример за event count и callback на всеки `N` импулса:

```python
from machine import Pin, PWM, Timer  # Импортираме Pin, PWM и Timer за броене на входни импулси.

signal_pwm = PWM(Pin("P107"), freq=200, duty=50)  # Генерираме входен тестов сигнал 200 Hz на P107.
timer = Timer(1)  # Използваме Timer(1) като хардуерен брояч на събития.

timer.init(mode=Timer.PERIODIC, period=20, callback=every_n_events_callback, hard=False)  # Искаме callback на всеки 20 импулса.
counter_channel = timer.channel(0, mode=Timer.IC, pin=Pin("P100"), measure=Timer.IC_EVENT_COUNT, edge=Timer.RISING)  # Пускаме channel(0) в event count режим.
print(counter_channel.capture())  # Четем частичния брой импулси в текущия прозорец.
```

- channel callback за `Timer.IC_EVENT_COUNT` няма
- `capture()` се ползва за polling на частичния брой

Тест 1: periodic и one-shot

- `Timer(1)` трябва да сработва многократно
- `Timer(2)` трябва да сработи само веднъж
- `Timer(1).counter()` трябва да се променя, докато таймерът работи
- проблем е ако one-shot не дойде или ако дойде повече от веднъж

Тест 2: output compare callback

- `Cycle-end callback count` трябва да расте
- `Compare A callback count` трябва да расте
- `Compare B callback count` трябва да расте
- проблем е ако cycle callback работи, а compare callback-ите стоят на `0`

Опционален хардуерен тест за output compare:

- за `Timer(1)` можеш да добавиш `pin=Pin("P500")` на `channel(1)`
- за `Timer(1)` можеш да добавиш `pin=Pin("P501")` на `channel(2)`
- на осцилоскоп очаквай събития около `1/4` и `3/4` от периода

Тест 3: input capture

- нужен е джъмпер `P107 -> P100`
- при PWM `1 kHz / 50% duty` очаквай `Измерен период` около `1000`
- при същия сигнал очаквай `Измерена high ширина` около `500`
- проблем е ако стойностите са `0`, силно шумни или high ширината е по-голяма от периода

Тест 4: event count

- нужен е джъмпер `P107 -> P100`
- входният PWM е `200 Hz`
- прозорецът е `20` импулса
- за около `1.1 s` очаквай приблизително `10` или `11` завършени прозореца
- `Частичен брой в текущия прозорец` трябва да е между `0` и `19`
- `Приблизителен общ брой импулси` трябва да е близо до `220`

Тук е важно:

- при `Timer.IC_EVENT_COUNT` няма channel callback
- `capture()` се ползва за polling на частичния брой
- базовият `Timer.callback()` се ползва когато искаш реакция на всеки `N` импулса

Ако нещо не работи:

- провери първо джъмпера `P107 -> P100`
- провери дали не е останал стар обект `PWM` или `Timer` от предишен тест
- извикай `deinit()` на използваните обекти и повтори теста
- ако `periodic` работи, но `compare` не работи, проблемът е в compare IRQ path-а
- ако `compare` работи, но `capture` и `event count` не работят, проблемът е в AGT input pin или input mode path-а

### Глава 17. Четене на бутон: `polling`, IRQ, `Timer(-1)`, debounce и събития

Тази глава събира на едно място реалните начини за работа с бутон върху `VK_RA4M2`.

Суровото четене на `SW1` е само началото.

Практическият въпрос е как да преведем шумния active-low вход към стабилни събития като:

- `PRESS`
- `RELEASE`
- `CLICK`
- `LONG_PRESS`
- `HOLD_START`
- `HOLD_REPEAT`

Първата идея е проста: `button.value()` ни дава ниво, но приложението почти винаги иска събития.

Пример с `polling` и преходи между стабилни състояния:

```python
raw_value = button.value()  # Четем суровата моментна стойност на бутона.
if raw_value != last_raw_value:  # Ако видим ново сурово ниво, започваме нов debounce прозорец.
    last_raw_value = raw_value  # Запомняме новата сурова стойност.
    raw_change_ms = now_ms  # Запомняме кога е започнала промяната.
if raw_value != stable_value and time.ticks_diff(now_ms, raw_change_ms) >= DEBOUNCE_MS:  # Ако новото ниво е стабилно достатъчно дълго, приемаме ново логическо състояние.
    stable_value = raw_value  # Обновяваме стабилното състояние на бутона.
    if stable_value == 0:  # Ако стабилното състояние е 0, имаме валидно натискане.
        print("EVENT: PRESS")  # Печатаме събитие за натискане.
    else:  # Ако стабилното състояние е 1, имаме валидно отпускане.
        print("EVENT: RELEASE")  # Печатаме събитие за отпускане.
```

Тук вече имаме важна промяна в начина на мислене:

- не гледаме „ниво в момента“
- гледаме „последно стабилно състояние“
- генерираме събитие само при стабилен преход

Ако искаме по-бърза реакция от чистото `polling`, ползваме прекъсване, но не правим тежката логика вътре в IRQ обработчика.

Пример с `IRQ_FALLING | IRQ_RISING` и отложена обработка:

```python
def button_irq_handler(pin_object):  # Това е краткият IRQ обработчик за суровите фронтове на бутона.
    irq_state_data["pending"] = 1  # Маркираме, че главният цикъл трябва да довърши логическата обработка.
    irq_state_data["deadline_ms"] = time.ticks_add(time.ticks_ms(), DEBOUNCE_MS)  # Отлагаме окончателното решение след debounce интервала.

if pending and time.ticks_diff(now_ms, deadline_ms) >= 0:  # Ако има чакаща работа и debounce прозорецът е изтекъл, вземаме стабилно решение.
    stable_candidate = button.value()  # Четем реалното ниво след краткото изчакване.
    if stable_candidate != previous_stable_value:  # Ако стабилното ниво реално е ново, генерираме логическо събитие.
        print("EVENT: PRESS" if stable_candidate == 0 else "EVENT: RELEASE")  # Печатаме кое логическо събитие е настъпило.
```

Това е по-добрият стил за бутон по прекъсване:

- IRQ само събужда логиката
- debounce се решава извън ISR
- събитието пак е стабилен `PRESS` или `RELEASE`, а не суров фронт

Третият подход е `Timer(-1)` като периодичен sampler.

Той е полезен, когато искаме еднакъв ритъм на пробовземане и по-богати събития за задържане.

Пример със софтуерен `Timer(-1)` и hold логика:

```python
soft_timer.init(period=SAMPLE_MS, mode=Timer.PERIODIC, callback=button_sample_callback)  # Стартираме Timer(-1) като периодичен sampler на бутона.
if timer_state["history"] == 0x00 and timer_state["stable_value"] != 0:  # Ако последните осем проби са 0, приемаме стабилно натискане.
    timer_state["event_code"] = EVENT_PRESS  # Записваме PRESS събитие за основния цикъл.
elif timer_state["stable_value"] == 0 and not timer_state["hold_started"] and time.ticks_diff(now_ms, timer_state["press_start_ms"]) >= LONG_PRESS_MS:  # Ако бутонът е натиснат достатъчно дълго, излъчваме начало на задържане.
    timer_state["event_code"] = EVENT_HOLD_START  # Записваме HOLD_START събитие.
elif timer_state["stable_value"] == 0 and timer_state["hold_started"] and time.ticks_diff(now_ms, timer_state["next_repeat_ms"]) >= 0:  # Ако вече сме в задържане и е дошло време за повторение, излъчваме repeat.
    timer_state["event_code"] = EVENT_HOLD_REPEAT  # Записваме HOLD_REPEAT събитие.
```

Тук се появяват вече различни класове събития:

- `PRESS` при стабилен преход `1 -> 0`
- `RELEASE` при стабилен преход `0 -> 1`
- `CLICK` при кратко натискане и отпускане
- `LONG_PRESS` при достигане на праг по време на задържане
- `HOLD_START` при началото на продължително задържане
- `HOLD_REPEAT` при периодично повтаряне, докато бутонът остава натиснат

Четвъртият подход е debounce чрез битово изместване.

Той е компактен и много удобен за периодичен sampler, защото свива последните `N` проби в една история.

Пример с shift-register debounce:

```python
history = ((history << 1) | button.value()) & 0xFF  # Преместваме историята наляво и добавяме новата проба като най-млад бит.
if history == 0x00 and stable_value != 0:  # Ако последните осем проби са натиснати, приемаме стабилно PRESS събитие.
    print("EVENT: PRESS")  # Печатаме събитие за натискане.
elif history == 0xFF and stable_value != 1:  # Ако последните осем проби са отпуснати, приемаме стабилно RELEASE събитие.
    print("EVENT: RELEASE")  # Печатаме събитие за отпускане.
```

Тук смисълът на `history` е директен:

- `0x00` означава осем поредни проби с натиснат бутон
- `0xFF` означава осем поредни проби с отпуснат бутон
- всички междинни стойности означават „още не е стабилно“

Практически избор на подход:

- ако искате най-простия старт, започнете с `polling`
- ако искате бързо събуждане на логиката, използвайте IRQ с отложена обработка
- ако искате равномерно пробовземане и hold/repeat семантика, използвайте `Timer(-1)`
- ако искате компактен debounce филтър, използвайте битово изместване

Пример за устойчиво състояние в `dataflash` и видима индикация с `LED1`:

```python
from machine import Pin  # Импортираме Pin за управление на LED1.
import dataflash  # Импортираме dataflash за устойчиво съхранение на състояние.

led = Pin("LED1", Pin.OUT, value=1)  # Използваме board alias-а LED1, започваме изгасен.
state = dataflash.read(0, 1)[0]  # Връщаме стойността на първия байт.

if state == 0x00:  # Ако предишният старт е записал 0x00, сега правим erase към 0xFF.
    dataflash.erase_block(0)  # Изтриваме блок 0, всички байтове стават 0xFF.
    blinks_per_sec = 2  # Бавно мигане означава erase.
else:  # Иначе приемаме, че байтът е 0xFF и записваме 0x00.
    dataflash.write(0, bytes([0x00]))  # Записваме 0x00 в първия байт.
    blinks_per_sec = 10  # Бързо мигане означава write.
```

Този пример показва как един байт в `dataflash` може да пази състояние между два старта на програмата.
За `VK_RA4M2` LED индикацията е върху `LED1`, защото провереният board LED е `P204` и е active-low.
При всяко стартиране се редуват две състояния:

- `0xFF` след `erase_block(0)`
- `0x00` след `write(0, bytes([0x00]))`

Скоростта на мигане показва кой преход е станал на текущия boot.

Тук се разграничават:

- файлова система
- block device
- отделен data flash регион

Проверени размери за текущата конфигурация на `VK_RA4M2`:

- MCU вариантът на тази платка е с общо `384 KB` code flash и `128 KB` RAM
- в текущия linker layout `290 KB` са отделени за firmware/application region, а `94 KB` са отделени като `FLASH_FS` за `/flash`
- отделно има `8 KB` `dataflash`
- `/flash` е върху вътрешния flash block device, монтиран като `FAT`; block size е `512 bytes`
- реално свободното място за файлове е малко по-малко от `94 KB`, защото част отива за самата файлова система

### Глава 25. Управление на паметта в MicroPython

Диагностичен пример:

```python
import gc  # Импортираме gc за контрол и измерване на garbage-collected heap-а.
import micropython  # Импортираме micropython за mem_info и други runtime helper-и.

gc.collect()  # Пускаме GC в предвидим момент, за да започнем от по-чисто състояние.
print(gc.mem_free(), gc.mem_alloc())  # Печатаме свободния и заетия heap.
micropython.mem_info()  # Печатаме обобщена информация за heap-а.
```

Буферен пример:

```python
buffer = bytearray(32)  # Създаваме един буфер, който ще преизползваме.
window = memoryview(buffer)[8:12]  # Вземаме прозорец към част от буфера без копиране.
window[0] = 123  # Променяме първия байт през memoryview.
print(list(buffer[8:12]))  # Показваме, че оригиналният буфер е променен на място.
```

Тук „управление на паметта“ не означава ръчно местене на адреси както в C, а по-скоро:

- да разбираме кои обекти заемат място в heap-а на MicroPython
- да различаваме RAM heap от stack, firmware и постоянна flash памет
- да ограничаваме излишните алокации в чувствителни по време участъци
- да преизползваме буфери вместо да създаваме нови обекти във всеки цикъл

Потвърдени факти за текущия `VK_RA4M2` порт:

- garbage-collected heap-ът се подава на MicroPython чрез linker символите `_heap_start` и `_heap_end`
- linker-ът заделя отделен фиксиран stack регион от `8 KB`
- `/flash` и `dataflash` са постоянна памет за файлове и данни, а не RAM heap за Python обекти

Практични API-та, които реално са налични в този порт:

- `gc.collect()` за принудително стартиране на garbage collector в удобен момент
- `gc.mem_free()` и `gc.mem_alloc()` за ориентир колко heap е свободен и колко е зает
- `gc.threshold()` за по-напреднал контрол кога да се задейства GC
- `micropython.mem_info()` и `micropython.mem_info(1)` за по-подробна картина на heap-а
- `micropython.alloc_emergency_exception_buf()` за изключително важни exception-и в interrupt/critical контекст
- `micropython.heap_lock()` и `micropython.heap_unlock()` за напреднали случаи, когато временно не трябва да се допуска алокация

Практически правила, които най-често дават реален ефект:

- правете `bytearray` веднъж и после го пълнете отново, вместо да създавате нов буфер всеки път
- използвайте `memoryview`, когато искате прозорец към част от буфера без копиране
- ако имате временни големи обекти, освобождавайте ги и извиквайте `gc.collect()` в предвидим момент, а не насред критична операция
- при interrupt-и, callbacks и latency-sensitive код избягвайте нови алокации; подгответе буферите предварително
- не смесвайте `machine.mem8/mem16/mem32` с управлението на Python heap-а; това са различни нива на достъп до паметта

```python
segment_pins = [Pin(name, Pin.OUT) for name in ("P105", "P104", "P113", "P114", "P115", "P304", "P303")]  # Това са седемте сегмента a..g.
```

### Глава 33. Tickless timers и sleep идея

Пример:

```python
import machine  # Импортираме machine за кратък lightsleep между събитията.
import time  # Импортираме time за работа с ticks_ms и ticks_diff.

tasks = [("lamp_timeout", 120), ("fan_timeout", 450), ("display_refresh", 40)]  # Подготвяме три задачи с различни крайни срокове в милисекунди.

next_deadline_ms = min(deadline for _, deadline in tasks)  # Избираме най-близкия срок като tickless цел.
sleep_ms = max(0, next_deadline_ms - time.ticks_diff(time.ticks_ms(), start_ms))  # Изчисляваме колко време може да се спи до следващото събитие.
machine.lightsleep(sleep_ms)  # Спим точно до най-близкото планирано събитие с lightsleep.
elapsed_ms = time.ticks_diff(time.ticks_ms(), start_ms)  # Изчисляваме изминалото време след съня.
ready_tasks = [task_name for task_name, deadline in tasks if deadline <= elapsed_ms]  # Избираме всички задачи, които вече са изтекли.
```

## Част XI: Външни модули по интерфейси

### Глава 37. Работа с външни модули по интерфейси

Тази глава не въвежда нов хардуерен контролер.

Тя събира вече видените `I2C`, `SPI` и `UART` в един практичен модел за мислене.

Когато включвате външен модул, не започвате от „готов driver“, а от четири по-базови въпроса:

1. С какво напрежение и логически нива работи модулът?
2. Кой интерфейс използва: `I2C`, `SPI` или `UART`?
3. Има ли допълнителни control линии като `CS`, `RST`, `INT`, `BUSY` или `EN`?
4. Кой е най-малкият безопасен probe, който доказва, че връзката работи?

На `VK_RA4M2` има три особено важни практични ограничения:

- `I2C(0)` дели `P400` със `SW1`
- `I2C(1)` дели `P100/P101` със `hardware SPI`
- `UART(9)` е най-удобният отделен канал, когато I2C или SPI вече са заети

Това значи, че изборът на интерфейс не е само логически, а и ресурсен.

Кога кой интерфейс е най-подходящ:

- `I2C` е удобен за сензори и по-бавни модули с адресирана обща шина
- `SPI` е удобен за по-бързи модули, при които имате отделен `CS` и frame-базиран обмен
- `UART` е удобен за модеми, GPS, Bluetooth и други модули с текстов или байтов поток

Практическият ред на работа почти винаги е един и същ:

1. Свържете `GND` и проверете напрежението
2. Проверете дали логическите нива на модула са съвместими с борда
3. Свържете сигналните линии на интерфейса
4. Свържете и нужните control линии
5. Стартирайте с минимална скорост и минимален probe
6. Едва след това четете идентификатор, статус или payload

Минимален `I2C` probe:

```python
from machine import I2C  # Импортираме I2C за базов probe на външна шина.

i2c = I2C(1, freq=100000)  # Създаваме I2C(1) на безопасни 100 kHz.
print(i2c.scan())  # Сканираме шината за адреси на свързани I2C модули.
```

Минимална `SPI` транзакция:

```python
from machine import SPI, Pin  # Импортираме SPI и Pin за frame-базиран обмен с външен модул.

cs = Pin("P103", Pin.OUT, value=1)  # Държим CS неактивен преди началото на транзакцията.
spi = SPI(0, baudrate=500000, polarity=0, phase=0, bits=8, sck=Pin("P102"), mosi=Pin("P101"), miso=Pin("P100"), cs=cs)  # Създаваме SPI с консервативни настройки.

spi.write_readinto(b"\x9F\x00\x00\x00", bytearray(4))  # Изпращаме команда и четем едновременно отговора.
cs.value(1)  # Освобождаваме модула след края на frame-а.
```

Минимален `UART` request/response:

```python
from machine import UART  # Импортираме UART за сериен обмен с външен модул.

uart = UART(9, 115200)  # Създаваме UART(9) с често срещана начална скорост.
uart.write(b"AT\r\n")  # Изпращаме примерна текстова команда към модула.

```

Общата идея е проста:

- `I2C` първо се доказва със `scan()`
- `SPI` първо се доказва с правилен `CS` и пълен frame
- `UART` първо се доказва с правилен `baud rate`, `TX/RX` и timeout

След това вече се минава към конкретния регистров модел или към конкретния текстов протокол на модула.

- за `UART` ви трябват `baud rate`, формат на кадъра и синтаксис на командите

### Глава 39. asyncio Event синхронизация

Пример:

```python
import asyncio  # Импортираме asyncio за кооперативна многозадачност.
from machine import Pin  # Импортираме Pin за реален хардуерен достъп.

LED_ON = 0  # Active-low: 0 = светва LED1.
LED_OFF = 1  # Active-low: 1 = гаси LED1.

button = Pin("SW1", Pin.IN, Pin.PULL_UP)  # SW1 = P400, вътрешен pull-up.
button_event = asyncio.Event()  # Създаваме Event обект за синхронизация между задачи.

async def button_producer():  # Тази задача следи SW1 и сигнализира при натискане.
    last_value = 1  # Последна стойност на бутона (ненатиснат).
    current_value = button.value()  # Четем SW1.
    if current_value == 0 and last_value == 1:  # Нов натиск (falling edge).
        button_event.set()  # Сигнализираме Event-а.

async def led_consumer():  # Тази задача чака Event и мига LED1.
    await button_event.wait()  # Чакаме Event-а (блокираме кооперативно).
    button_event.clear()  # Нулираме Event-а за следващо използване.
```

Тук се вижда:

- `asyncio.Event` за комуникация между задачи
- производител-консуматор модел
- кооперативно блокиране без busy-wait

- Това е важна крачка от „много задачи“ към „задачи, които си взаимодействат правилно“.

## Част XIII: Специализирани светлинни модули

### Глава 40. NeoPixel

`NeoPixel` е удобен пример за „умен“ външен RGB светодиоден модул.

Той не се управлява като обикновен RGB LED с три PWM канала.

Вместо това се използва един data проводник с точно времедиаграмиране, което MicroPython крие зад модула `neopixel`.

В този курс използваме:

- `P500` като задължителен enable pin за модула в този setup
- `P112` като `DIN` data линия
- `1` пиксел за най-простия тест

Това е удобно за демонстрация, но има важно уточнение:

- `P500` трябва да бъде включен задължително в този setup
- при по-дълга лента или по-голям ток може да е нужно отделно основно захранване
- при отделно захранване масата пак трябва да е обща с борда

Ключовата идея е, че работата с `NeoPixel` минава през три стъпки:

1. Включвате захранването на модула
2. Записвате RGB стойност в буфера
3. Извиквате `write()`, за да се изпрати timed bitstream към пиксела

Минимален пример:

```python
from machine import Pin  # Импортираме Pin за power-enable и data линията.
import neopixel  # Импортираме neopixel драйвера за RGB модула.

vcc = Pin("P500", Pin.OUT, value=1)  # Включваме P500, защото без него модулът не е активен в този setup.
np = neopixel.NeoPixel(Pin("P112"), 1)  # Създаваме NeoPixel обект за един пиксел върху P112.
np[0] = (40, 0, 0)  # Зареждаме червено в буфера на първия пиксел.
np.write()  # Изпращаме буфера и реално сменяме цвета на модула.
```

Тук има две практични разлики спрямо обикновен GPIO или PWM пример:

- цветът се задава като кортеж `(R, G, B)`
- промяната не се вижда преди `write()`

Втори важен практически момент е яркостта.

В учебните примери стойностите са ниски, например `40`, за да се ограничи токът и да се намали рискът при първи тест.

Трети важен момент е, че `NeoPixel` е външен модул, така че физическото свързване е толкова важно, колкото и кодът:

- `DIN` на модула трябва да отиде към `P112`
- `P500` трябва да е включен
- захранването трябва да е стабилно
- ако се ползва отделно основно захранване, масата трябва да е обща с борда

### Глава 41. WS2812 през `machine.WS2812` и SCI TX-only

`WS2812B` е от същото семейство адресируеми RGB светодиоди, но в този порт вече има и втори начин за управление.

Вместо класическия `neopixel` модул с `machine.bitstream()`, може да се използва `machine.WS2812`.

Този драйвер кодира данните през подходящ `SCI` канал и извежда само data сигнала през избрания `TXD/MOSI` pin.

Практически това означава:

- към самия светодиоден модул свързвате само `DIN` към избрания data pin
- не подавате външен `SCK` и `MISO` към лентата
- продължавате да работите с буфер и `write()`, почти както при `NeoPixel`

От гледна точка на Python кодът е еднопроводен: има само data pin към модула.

От гледна точка на микроконтролера вътрешно се използва `SCI` хардуерът, така че избраният pin автоматично определя кой `SCI` блок ще бъде зает.

В текущата работеща реализация timing-ът вече не се прави с по-старото `3-bit` кодиране.

Сега драйверът използва:

- вътрешен `SCI` поток около `2.857143 MHz`
- `5-bit` кодиране за всеки логически WS2812 бит
- кратък скрит `LOW` prefix преди payload-а
- достатъчно дълъг `LOW` suffix за `latch/reset`
- непрекъснат `DTC` feed, за да няма байтови дупки в натоварена `IRQ` среда

Това е важно, защото от Python страна API-то си остава просто:

- пишете RGB стойности в буфера
- извиквате `write()`
- не мислите за ръчно bit timing управление

От практическа гледна точка е най-добре да започнете с дефолтните параметри на драйвера и да не задавате `baudrate`, освен ако нямате конкретна експериментална причина.

Поддържаните data pin-ове в този порт са:

- `SCI0` -> `P101`, `P205`, `P411`
- `SCI1` -> `P213`, `P401`, `P501`
- `SCI2` -> `P102`, `P112`, `P302`
- `SCI9` -> `P109`, `P203`, `P409`, `P602`

Това значи, че `P112` вече е default pin, но не е единствен възможен.

Важното ограничение е по канали, не само по pin.

Ако изберете pin от `SCI2` групата, не трябва едновременно да очаквате:

- `machine.WS2812`
- `UART(2)`
- `SPI(2)` през `SCI2`

Същата логика важи и за другите групи, ако вече ползвате същия `SCI` канал за друг интерфейс.

Минимален пример с алтернативен pin:

```python
from machine import Pin  # Импортираме Pin за захранването и data линията.
from machine import WS2812  # Импортираме специализирания драйвер за WS2812.
import time  # Импортираме time за кратко изчакване след включване на захранването.

vcc = Pin("P500", Pin.OUT, value=1)  # Включваме P500, защото без него модулът не е активен в този setup.
time.sleep_ms(100)  # Изчакваме power-enable линията и модулът да се стабилизират.
strip = WS2812(pixel_count=1, pin=Pin("P109"), channels=3)  # Създаваме драйверен обект върху алтернативния pin P109.
strip[0] = (40, 0, 0)  # Зареждаме червено в буфера на първия пиксел.
strip.write()  # Изпращаме буфера към модула през SCI TX-only backend-а.
```

Подобно на `NeoPixel`, и тук цветът не се вижда преди `write()`.

Разликата е, че тук timing-ът не идва от общия bitstream механизъм, а от специализиран C-side драйвер в порта.

Това е полезно по три причини:

- API-то е ясно вързано към `WS2812`
- можете да изберете удобен `SCI TX/MOSI` pin според реалното окабеляване
- логиката за кодиране, непрекъснато предаване и latch остава в C, а не в Python

Важно е и захранването:

- в този setup `P500` трябва да бъде включен задължително
- при повече пиксели може да е нужно отделно основно захранване, но `P500` остава включен
- масата на захранването и масата на борда трябва да са общи

Практически работен ред е:

1. Започнете с `pixel_count=1`.
2. Проверете последователно `red`, `green`, `blue`, `white`, `off`.
3. Едва след това минете към повече пиксели или матрица.

Важното ограничение е, че този драйвер е порт-специфичен.

Тоест примерите са силно полезни точно за `VK_RA4M2`, но не бива да очаквате същия `machine.WS2812` API на произволен друг MicroPython порт.

#### Резюме
- Главата показва `WS2812` като специализиран `machine` клас, реализиран в този порт върху няколко `SCI TX/MOSI` pin групи.
- За самото свързване към модула е нужен само избраният data pin, без външен clock pin към светодиода.
- Конфликтите са по `SCI` канал: не може един и същ `SCI` блок да се дели едновременно от `WS2812` и `UART` или `SPI`.

#### Самопроверка
1. Каква е разликата между `neopixel.NeoPixel` и `machine.WS2812` в този порт?
2. Защо потребителят свързва само `DIN -> избрания TXD/MOSI pin`, въпреки че вътрешно драйверът използва `SCI`?
3. Какво общо имат `P109` и `UART(9)` при използване на `machine.WS2812`?

#### Упражнения
1. Пуснете един и същ пример веднъж с `P112`, а после с `P109`, и сравнете нужните промени в Python кода.
2. Променете `pixel_count` на `2` или `4` и направете цветен „марш“ по къса лента.
3. Изберете pin от `SCI0` или `SCI1` групата и проверете кои други интерфейси вече не бива да активирате едновременно.
4. Пуснете `examples/ws2812_sci_chase_145.py` върху `1 + 12*12` светодиода, като държите `P500` включен и осигурите достатъчно основно захранване, и наблюдавайте дали трите цвята се местят равномерно.

#### Ако не работи
- Симптом: няма никаква светлина. Проверка: вижте дали `P500` реално подава захранване и дали `DIN` е към правилния вход на модула.
- Симптом: получавате грешка за зает bus. Проверка: избраният `SCI` канал може вече да е зает от `UART` или `SPI` със същия номер.
- Симптом: цветовете са нестабилни при повече пиксели. Проверка: осигурете отделно основно захранване и обща маса, но не изключвайте `P500`.
- Симптом: няма светлина на матрицата. Проверка: уверете се, че `P500` е включен и че масата е обща.
- Симптом: `neopixel` примерът работи, а този не. Проверка: това е индикация, че точно избраният `SCI TX/MOSI` path трябва да се валидира на реален хардуер.

#### Нататък
След тази глава прегледайте каталога на примерите и изберете дали да останете с универсалния `neopixel` подход, или с порт-специфичния `machine.WS2812` с runtime избор на data pin.

## Какво още не е потвърдено на реален борд

Книгата и примерите са прегледани за пълност и са подредени спрямо плана.

Още не е потвърдено пълно runtime изпълнение на всички примери върху реален `VK_RA4M2`.

Най-чувствителните места остават:

- външните I2C устройства
- SPI loopback и външни SPI модули
- външните UART модули и AT-подобни текстови протоколи
- NeoPixel модулът върху `P500/P112`, особено при по-дълги проводници или повече от един пиксел
- WS2812 path-ът през `machine.WS2812` и различните `SCI TX/MOSI` pin-ове, защото е нов порт-специфичен backend и трябва да се потвърди на реален хардуер
- 7-сегментната индикация и матричната клавиатура
- write режимите на `Flash` и `dataflash`
- `lightsleep` и `deepsleep`

## Заключение

Тази версия на книгата е построена като проверка за пълност:

- всички теми от плана са отразени
- всички `67` примерни файла са споменати изрично
- всяка голяма тема има поне един реален кодов откъс
- порт-специфичните ограничения на `VK_RA4M2` са записани ясно

Следващата разумна стъпка вече не е „още съдържание“, а хардуерна валидация на примерите по групи върху реалната платка.
