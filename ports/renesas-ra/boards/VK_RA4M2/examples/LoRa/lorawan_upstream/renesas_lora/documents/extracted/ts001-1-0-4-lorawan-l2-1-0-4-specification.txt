275   1 Introduction
276   This document describes the LoRaWAN® network protocol, which is optimized for battery-
277   powered end-devices that may be either mobile or mounted at a fixed location.
278   LoRaWAN networks are typically laid out in a star-of-stars topology in which gateways1 relay
279   transmissions between end-devices and a central Network Server at the backend. Gateways
280   are connected to a Network Server via standard IP connections, whereas end-devices use
281   single-hop radio-frequency (RF) communication to one or many gateways. All communication
282   is generally bi-directional, although uplink communication from an end-device to a Network
283   Server is expected to be the predominant traffic.
284   Communication between end-devices and gateways is distributed over different frequency
285   channels and data rates. Selecting the data rate is a tradeoff between communication range
286   and transmission duration; communications with different LoRa data rates do not interfere with
287   each other. To maximize both the battery life of end-devices and the overall network capacity,
288   the LoRaWAN network infrastructure MAY manage the data rate and RF transmit power for
289   each end-device individually by means of an adaptive data rate (ADR) scheme.
290   An end-device may transmit on any channel available at any time using any available data
291   rate, as long as the following rules are observed:
292    The end-device changes channels in a pseudo-random fashion for every transmission. The
293     resulting frequency diversity makes the system more robust to interference.
294    The end-device pseudo-randomly changes its transmit periodicity to prevent systematic
295     synchronization of populations of end-device transmissions.
296    The end-device complies with all local regulations governing its behavior in the band and
297     sub-bands in which it is currently operating including, but not limited to, duty-cycle and dwell-
298     time (transmit-duration) limitations.
299   All LoRaWAN end-devices SHALL implement at least Class A functionality as described in
300   this document. In addition, they MAY implement Class B and/or Class C as also described in
301   this document.
302   End-devices implementing Class B are referred to as Class B-capable. When operating in
303   Class B, end-devices are referred to as Class B-enabled. Transition from Class B-disabled to
304   Class B-enabled is called switching to Class B.
305   End-devices implementing Class C are referred to as Class C-capable. When operating in
306   Class C, end-devices are referred to as Class C-enabled. Transition from Class C-disabled to
307   Class C-enabled is called switching to Class C.
308   In all cases, end-devices remain compatible with Class A.

326   2 Introduction to LoRaWAN Options
327   LoRa® is a wireless modulation for long-range, low-power, low-data-rate applications
328   developed by Semtech. End-devices implementing more than Class A are generally called
329   “higher Class end-devices” in this document.


330   2.1 LoRaWAN Classes
331   A LoRaWAN network distinguishes between a basic LoRaWAN (called Class A) and optional
332   features (Class B, Class C …) as shown in Figure 1.
333
334




335
336                                    Figure 1: LoRaWAN Classes

337

338    Bi-directional end-devices (Class A): Class A end-devices allow bi-directional
339     communications, whereby each end-device’s uplink transmission is followed by two short
340     downlink receive windows. The transmission slot scheduled by the end-device is based on
341     its own communication needs, with a small variation based on a random time basis (ALOHA-
342     type protocol). Class A operation is the lowest-power end-device system for applications
343     that require only downlink communication from the server shortly after the end-device has
344     sent an uplink transmission. Downlink communications from the server at any other time will
345     have to wait until the next uplink initiated by the end-device.
346    Bi-directional end-devices with scheduled receive slots (Class B): Class B-capable
347     end-devices allow more receive slots. In addition to Class A receive windows, Class B-
348     enabled end-devices open extra receive windows at scheduled times. In order for the end-
349     device to open its receive windows at a scheduled time, it receives a time-synchronized
350     beacon from the gateway. This allows the Network Server to know when the end-device is
351     listening.

355     B-enabled, but they feature the lowest latency for communication between servers and end-

366   3 Physical Packet Formats
367   The physical layers used by LoRaWAN are defined in [RP002].
368   The LoRaWAN terminology distinguishes between uplink and downlink frames.


369   3.1 Uplink Packets
370   Uplink packets are sent by end-devices to a Network Server relayed by one or many
371   gateways.


372   3.2 Downlink Packets
373   Downlink packets are sent by a Network Server to only one end-device and are transmitted
374   by a Network Server through one or more gateways.2


375   3.3 Receive Windows
376   Following each uplink transmission, the end-device SHALL open one or two receive windows
377   (RX1 and RX2); if no packet destined for the end-device is received in RX1, it SHALL open
378   RX2. The receive windows start times are defined using the end of the transmission as a
379   reference, see Figure 2.
380




381
382                                  Figure 2: End-device receive-slot timing

383



384   3.3.1 Receiver activity during receive windows
385   If a preamble is detected during one of the receive windows, the radio receiver SHOULD stay
386   active until the downlink frame is demodulated. If a frame was detected and subsequently
387   demodulated during the first receive window, and the frame was intended for this end-device
388   after address and MIC (message integrity code) checks, the end-device SHALL NOT open
389   the second receive window.

390   3.3.2 First receive-window channel, data rate, and start
391   The first receive window RX1 uses a frequency that is a function of the uplink frequency and
392   a data rate that is a function of the uplink data rate. RX1 SHALL be open no longer than
393   RECEIVE_DELAY1 seconds after the end of the uplink modulation.3 The relationship between
394   uplink and RX1 data rates is region-specific and detailed in the “LoRaWAN Regional
395   Parameters” [RP002] document.


396   3.3.3 Second receive window channel, data rate, and start
397   The second receive window RX2, if opened (see Section 3.3.1), uses a fixed configurable
398   frequency and data rate, and SHALL be open no longer than RECEIVE_DELAY2 seconds
399   after the end of the uplink modulation.3 The frequency and data rate can be modified by MAC
400   commands (see Section 5). The default frequency and data rate are region-specific and
401   detailed in “LoRaWAN Regional Parameters” [RP002].


402   3.3.4 Receive window duration
403   The duration of a receive window SHALL be at least the time required by the end-device’s
404   radio transceiver to detect a downlink preamble starting at RECEIVE_DELAY1 or
405   RECEIVE_DELAY2 after the end of the uplink modulation.
406

407              Note: The end-device receive window duration has to accommodate the
408              maximum potential imprecision of the end-device’s clock. The delay
409              between the end of the uplink and the start of the receive windows can
410              be changed from 1s to 15s for RX1 (and thereby from 2s to 16s for RX2)
411              using the OTAA (over-the-air activation) Join-Accept frame or the
412              RXTimingSetupReq MAC command. Therefore, this delay must be
413              accommodated when computing the maximum clock imprecision.
414              Example: A 30 ppm XTAL frequency error translates to ±30 µs after 1 s
415              and ±450 µs after 15 s.

423   timing and receive parameters.

517   4.3.1.1 Adaptive data-rate control in frame header (ADR, ADRACKReq in FCtrl)
518   LoRaWAN allows end-devices to use any of the possible data rates and transmit (TX) power
519   individually. This feature is used by Network Servers to adapt and optimize the number of
520   retransmissions, the data rate, and the TX power of end-devices. This is referred to as the
521   adaptive data rate (ADR) and, when it is enabled, end-devices will be optimized to use the
522   fastest data rate and minimum TX power possible.
523   ADR control may not be possible when radio channel attenuation changes rapidly and/or
524   continuously. When the Network is unable to control the data rate of an end-device, the end-
525   device’s application layer SHOULD control it. It is RECOMMENDED that a variety of different
526   data rates be used in this case. The application layer SHOULD always try to minimize the
527   aggregated airtime, given the network conditions.
528   If the uplink ADR bit is set, the Network may control the number of retransmissions, the data
529   rate, and the TX power of the end-device through the appropriate MAC commands. If the ADR
530   bit is unset, the Network Server SHALL accept that the end-device MAY not comply with any
531   attempt to control the number of retransmissions, the data rate, or the TX power of the end-
532   device regardless of the received signal quality. The Network MAY still send commands to
533   inform the end-device of the recommended configuration using the LinkADRReq command.
534   An end-device SHOULD accept the channel mask controls present in LinkADRReq, even
535   when the ADR bit is not set. The end-device SHALL respond to all LinkADRReq commands
536   with a LinkADRAns indicating which command elements were accepted and which were
537   rejected. This behavior differs from when the uplink ADR bit is set, in which case the end-
538   device accepts or rejects the entire command.
539

540              Note: A Network Server may not infer any actual end-device state in the
541              case where the uplink ADR bit is not set, regardless of the state of the
542              individual Status bits of LinkADRAns. These are provided for offline
543              debugging.
544

545   When the downlink ADR bit is set, it informs the end-device that the Network Server is able to
546   send ADR commands. The end-device MAY set/unset the uplink ADR bit independently.
547   When the downlink ADR bit is unset, it signals the end-device that, owing to rapid changes of
548   the radio channel, the Network temporarily cannot estimate the best data rate. In that case,
549   the end-device has the choice to
550    Unset the ADR uplink bit and control its uplink data rate, TX power and channel plan
551     following its own strategy. This SHOULD be the typical strategy for a mobile end-device, or
552    Ignore it (keep the uplink ADR bit set) and apply the normal ADR backoff algorithm in the
553     absence of downlinks. This SHOULD be the typical strategy for a stationary end-device.

618   When receiving a confirmed data frame, the receiver responds with a data frame that has the
619   acknowledgment bit (ACK) set. If the Network receives such a confirmed frame it SHOULD
620   send an acknowledgment. If the Network sends an acknowledgement it SHALL send it using
621   one of the Class A receive windows opened by the end-device after the send operation. If an
622   end-device receives such a confirmed frame in one of its Class A receive windows, it SHALL
623   transmit an acknowledgment with its next uplink. If an end-device receives such a confirmed
624   frame outside of its Class A receive windows, i.e. in a Class B ping slot (see section 9) or in
625   RXC (see section 15), it SHOULD send an acknowledgement.
626   Acknowledgments SHALL only be sent in response to the latest frame received and SHALL
627   NOT be transmitted more than NbTrans times. The Network SHALL only send an
628   acknowledgment in the Class A receive windows (RX1/RX2) of the confirmed uplink that
629   requested it.

637   4.3.1.3 Retransmission procedure
638   Downlink frames
639   A downlink confirmed or unconfirmed frame SHALL NOT be retransmitted using the same
640   frame counter value. In the case of a confirmed downlink, if the acknowledge is not received,
641   the Application Server is notified and may decide to transmit a new confirmed frame.
642
643   Uplink frames
644   Uplink confirmed and unconfirmed frames are transmitted NbTrans times (see Section 5.2)
645   unless a valid Class A downlink is received following one of the transmissions. The NbTrans
646   parameter can be used by a Network Server to control the redundancy of end-device uplinks
647   to achieve a given quality of service. An end-device SHALL perform frequency hopping as
648   usual between repeated transmissions. It SHALL wait after each repetition until the receive
649   windows have expired. The delay between retransmissions is at the discretion of the end-
650   device and MAY be different for each end-device. When an end-device has requested an ACK
651   from the Network but has not yet received it, it SHALL wait RETRANSMIT_TIMEOUT seconds
652   after RECEIVE_DELAY2 seconds have elapsed after the end of the previous uplink
653   transmission before sending a new uplink (repetition or new frame). The
654   RETRANSMIT_TIMEOUT delay is not required between unconfirmed uplinks, or after the ACK
655   has been successfully demodulated by the end-device. The RETRANSMIT_TIMEOUT value
656   is given in [RP002]. The retransmission backoff mechanism, defined in Section 7, may also
657   extend the interval between retransmissions, if applicable.
658   End-devices SHALL stop any further retransmission of an uplink confirmed frame if a
659   corresponding downlink acknowledgment frame is received.
660   End-devices SHALL also stop any further retransmission of an uplink unconfirmed frame
661   whenever a valid downlink frame is received in a Class A receive window.
662   If the Network receives more than NbTrans transmissions of the same uplink frame having
663   the ADR bit set, this may indicate a replay attack or a malfunctioning end-device, and therefore
664   the Network SHALL silently discard the extra frames.
665

666              Note: A Network Server that detects a replay attack may take additional
667              measures, such as reducing the NbTrans parameter to 1 or discarding
668              uplink frames received over a channel that was already used by an
669              earlier transmission of the same frame, or by some other unspecified
670              mechanism.

678   4.3.1.5 Frame counter (FCnt)
679   There are two frame counters for each end-device. FCntUp is incremented by an end-device
680   when a data frame is transmitted to a Network Server (uplink). FCntDown is incremented by
681   a Network Server when a data frame is transmitted to an end-device (downlink). The Network
682   Server tracks the uplink frame counter and generates the downlink counter for each end-
683   device.
684   Whenever an OTAA end-device successfully processes a Join-Accept frame, the frame
685   counters on the end-device (FCntUp) and the Network side (FCntDown) are reset to 0.
686   For ABP (activation by personalization) end-devices, the frame counters are initialized to 0 by
687   the manufacturer. ABP end-devices SHALL NOT reset the frame counters during the end-
688   device’s lifetime. If the end-device is susceptible to losing power during its lifetime (battery
689   replacement, for example), the frame counters SHALL persist during such an event.
690   Subsequently, FCntUp is incremented with each uplink and FCntDown is incremented with
691   each downlink. At the receiver side, the corresponding counter is kept in sync with the received
692   value, provided the received value has been incremented compared to the current counter
693   value, and the frame MIC field matches the MIC value computed locally using the appropriate
694   network session key. FCntUp SHALL NOT be incremented in the case of multiple
695   transmissions of a confirmed or unconfirmed frame (see NbTrans parameter). Network
696   Servers SHALL drop the application payload of the retransmitted frames and only forward a
697   single instance to the appropriate Application Server.
698   A first uplink with FCntUp=0 sent by an ABP or an OTAA end-device after a successful Join
699   procedure SHALL be accepted by a Network Server, provided the MIC field is valid.
700   Analogously, a first downlink with FCntDown=0 sent by a Network Server to an ABP or an
701   OTAA end-device after a successful Join procedure SHALL be accepted by the end-device,
702   provided the MIC field is valid.
703   Frame counters are 32 bits wide. The FCnt field SHALL correspond to the least-significant
704   16 bits of the 32-bit frame counter (i.e., FCntUp for data frames sent uplink and FCntDown
705   for data frames sent downlink).
706   The end-device SHALL NOT reuse the same FCntUp value with the same application or
707   network session keys, except for retransmission.
708   The end-device SHALL NOT process any retransmission of the same downlink frame.
709   Subsequent retransmissions SHALL be ignored without being processed.

1323   6 End-Device Activation
1324   To participate in a LoRaWAN network, each end-device SHALL be personalized and
1325   activated.
1326   Activation of an end-device can be achieved in two ways, either via Over-The-Air Activation
1327   (OTAA) when an end-device is deployed or reset, or via Activation By Personalization (ABP)
1328   in which the two steps of end-device personalization and activation are performed in one step.
1329   An end-device SHALL implement either OTAA or ABP, and MAY implement both OTAA and
1330   ABP.


1331   6.1 Data Stored in End-Device after Activation
1332   After activation, the following information is stored in the end-device: a device address
1333   (DevAddr), a network session key (NwkSKey), and an application session key (AppSKey).


1334   6.1.1 End-device address (DevAddr)
1335   The DevAddr consists of 32 bits and identifies the end-device within the current network.
1336   The DevAddr is allocated by the Network Server of the end-device.

1363   6.1.2 Network session key (NwkSKey)
1364   NwkSKey is a network session key specific to the end-device. It is used by both the Network
1365   Server and the end-device to calculate and verify the MIC (message integrity code) of all data
1366   frames to ensure data integrity. It is further used to encrypt and decrypt the payload field of
1367   MAC-only data frames, where FPort=0.
1368   NwkSKey SHOULD be stored such that extraction and re-use by malicious actors is
1369   prevented.


1370   6.1.3   Application session key (AppSKey)
1371
1372   AppSKey is an application session key specific to the end-device. It is used by both the
1373   Application Server and the end-device to encrypt and decrypt the payload field of application-
1374   specific data frames. Application payloads SHALL be encrypted end-to-end between the end-
1375   device and the Application Server, but they are integrity-protected only over-the-air and not
1376   end-to-end. This means that a Network Server may be able to alter the encrypted content of
1377   the data frames in transit (yet without being able to read the plain content). Network servers
1378   are considered to be trusted, but it is RECOMMENDED that applications wishing to implement
1379   end-to-end confidentiality and integrity protection use additional end-to-end security solutions,
1380   which are beyond the scope of this specification.
1381   AppSKey SHOULD be stored such that extraction and re-use by malicious actors is
1382   prevented.


1383   6.2 Over-the-Air Activation
1384   For over-the-air activation, end-devices SHALL follow a Join Procedure prior to participating
1385   in data exchanges with a Network Server. An end-device SHALL initiate a new Join Procedure
1386   every time it loses the session context information.
1387   An end-device SHALL be personalized with the following information before it starts the Join
1388   procedure: a globally unique end-device identifier (DevEUI), the Join Server identifier
1389   (JoinEUI), and an AES-128 key (AppKey).
1390   The JoinEUI is described below in Section 6.2.2.
1391



        © 2020 LoRa Alliance®                    Page 43 of 90           The authors reserve the right to change
                                                                              specifications without notice.
                                                                      LoRaWAN® L2 1.0.4 Specification



1392               Note: For over-the-air-activation, end-devices are not personalized with
1393               any kind of network key. Instead, whenever an end-device joins a
1394               network, a network session key specific to that end-device is derived to
1395               encrypt and verify transmissions at the network level. This facilitates
1396               roaming of end-devices between networks of different providers.
1397               Furthermore, using both a network session key and an application
1398               session key allows federated Network Servers in which application data
1399               cannot be read by the network provider.


1400   6.2.1 End-device identifier (DevEUI)
1401   DevEUI is a global end-device ID in the IEEE EUI64 address space that uniquely identifies
1402   the end-device across roaming networks.
1403   All end-devices SHALL have an assigned DevEUI, regardless of which activation procedure
1404   is used (i.e., ABP or OTAA).
1405   For OTAA end-devices, DevEUI SHALL be stored in the end-device before the Join
1406   procedure is executed. For ABP end-devices, DevEUI SHOULD be stored in the end-device
1407   itself.
1408               Note: It is a recommended practice that DevEUI should also be
1409               available on an end-device label for the purpose of end-device
1410               administration.


1411   6.2.2 Join-Server identifier (JoinEUI)
1412   JoinEUI is a global application ID in the IEEE EUI64 address space that uniquely identifies
1413   the Join-Server that is able to assist in the processing of the Join procedure and the derivation
1414   of session keys.
1415   For OTAA end-devices, JoinEUI SHALL be stored in the end-device before the Join
1416   procedure is executed. JoinEUI is not required for ABP-only end-devices.


1417   6.2.3 Application key (AppKey)
1418   The AppKey is an AES-128 root key specific to the end-device.8 Whenever an end-device
1419   joins a network via over-the-air activation, the AppKey is used to derive the session keys
1420   NwkSKey and AppSKey specific to that end-device to encrypt and verify network
1421   communication and application data.
1422   An AppKey SHALL be stored on an end-device intending to use the OTAA procedure.
1423   An Appkey is NOT REQUIRED for ABP-only end-devices.

1426   exchanged with the server, namely a Join-Request and a Join-Accept.

1552   6.3 Activation by Personalization
1553   Activation by personalization ties an end-device directly to a specific network, thus bypassing
1554   the Join-Request – Join-Accept procedure.
1555   Activating an end-device by personalization means that the DevAddr and the two session
1556   keys NwkSKey and AppSKey are stored directly in the end-device instead of being derived
1557   from DevEUI, JoinEUI and the AppKey. The end-device is equipped with the required
1558   information for participating in a specific LoRaWAN network as soon as it is started.
1559   Each end-device SHALL have a unique set of NwkSKey and AppSKey values.
1560   Compromising the keys of one end-device SHALL NOT compromise the security of the
1561   communications of other end-devices. The process to build those keys SHALL be such that
1562   the keys cannot be derived in any way from publicly available information such as the end-
1563   device address or DevEUI.
1564   Upon first boot and following a reset, personalized end-devices SHALL have all available
1565   channels for that region enabled and SHOULD use all required data rates for that region.
1566   Configurations of the end-device by the Network that controls downlink connectivity (controlled
1567   by RXParamsSetupReq, DlChannelReq, RXTimingSetupReq, and TXParamSetupReq)
1568   SHALL be persisted by the end-device, even after a reset.
1569   Frame counter values SHALL be used only once in all invocations of a same key with the
1570   CCM* (Counter with CBC Message Authentication Code) mode of operation [IEEE802154].
1571   Therefore, re-initialization of an ABP end-device frame counters is forbidden. ABP end-
1572   devices SHALL store the frame counters persistently (e.g., in non-volatile memory).
1573

1574              Note: ABP end-devices use the same session keys throughout their
1575              lifetime (i.e., no rekeying is possible). Therefore, it is recommended that
1576              OTAA end-devices be used for higher security applications.

1603   8 Introduction to Class B
1604   This section describes the LoRaWAN Class B layer, which is optimized for battery-powered
1605   end-devices that may be either mobile or mounted at a fixed location.
1606   End-devices SHOULD implement Class B operation when there is a requirement to open
1607   receive windows at fixed time intervals for the purpose of enabling network-initiated downlink
1608   frames. Class B-capable end-devices SHALL NOT enable Class B and Class C operation
1609   concurrently.
1610   LoRaWAN Class B option adds a synchronized reception window on the end-device.
1611   One of the limitations of LoRaWAN Class A is the ALOHA method of sending data from the
1612   end-device; it does not allow for a known reaction time when the customer application or the
1613   server wants to address the end-device. The purpose of Class B is to have an end-device
1614   available for reception at a predictable time, in addition to the reception windows that follows
1615   the random uplink transmission from the end-device of Class A. Class B is achieved by having
1616   the gateway send a beacon on a regular basis to synchronize all end-devices in the network
1617   so that the end-device can open a short additional reception window (called a ping slot) at a
1618   predictable time during a periodic time slot.
1619

1620              Note: The decision to switch from Class A to Class B comes from the
1621              application layer of the end-device. If this switch from Class A to Class
1622              B has to be controlled from the network side, the customer application
1623              must use one of the end-device’s Class A uplinks to send back a
1624              downlink to the application layer, and it needs the application layer on
1625              the end-device to recognize this request—this process is not managed
1626              at the LoRaWAN level.


1627   8.1 Principle of Synchronous Network-initiated Class B Downlinks
1628   For a network to support end-devices of Class B, the Network SHALL broadcast a beacon that
1629   provides a timing reference to end-devices. Based on this timing reference, the Class B-
1630   enabled end-devices SHALL periodically open receive windows, hereafter called ping slots,
1631   which can be used by the Network to initiate a downlink communication. A Network-initiated
1632   downlink using one of these ping slots is called a ping. The gateway chosen to initiate this
1633   downlink communication is selected by the Network Server. For this reason, if an end-device
1634   moves and detects a change in the identity advertised in the received beacon, it SHALL send
1635   an uplink to the Network Server so that the server can update the downlink routing path
1636   database.
1637   When enabling Class B mode, an end-device SHALL use the defined values for the following
1638   parameters:
1639    Default ping-slot periodicity
1640    Default ping-slot data rate
1641    Default ping-slot channel.

1642   These parameters have default values defined in the “Regional Parameters Specification”
1643   [RP002] and MAY be updated via Class B MAC commands (cf. Section 12).
1644   All end-devices start and join the network as Class A end-devices with Class B disabled. The
1645   end-device application can then decide to enable Class B. Class B-capable end-devices still
1646   implement all functionalities of Class A end-devices. In particular, Class B-enabled end-
1647   devices SHALL respect the Class A RX1 and RX2 receive window definition following every
1648   uplink (cf. Section 3.3).

1649   Class B is enabled by the following process:
1650    The end-device application requests the LoRaWAN layer to enable Class B mode. The
1651    LoRaWAN layer in the end-device searches for a beacon. To accelerate beacon discovery,
1652    the LoRaWAN layer MAY use the DeviceTimeReq MAC command.
1653    Once the end-device has found a beacon, it MAY enable Class B mode.
1654    Once Class B is enabled, the MAC layer SHALL set to 1 the ClassB bit of the FCtrl field
1655    of every uplink frame transmitted to remain Class B-enabled. This bit signals to the server
1656    that the end-device has enabled Class B.
1657    The MAC layer SHOULD autonomously schedule a reception slot for each beacon and each
1658    ping slot. The end-device SHALL take into account the maximum possible clock drift in the
1659    scheduling of the beacon reception slot and ping slots. When a downlink is successfully
1660    demodulated during a ping slot, it SHALL be processed similarly to a downlink as described
1661    in the LoRaWAN Class A specification.
1662    A mobile end-device SHOULD periodically inform the Network Server of its location to
1663    update the downlink route. This is done by transmitting a normal (possibly empty)
1664    unconfirmed or confirmed uplink. The end-device LoRaWAN layer SHALL appropriately set
1665    the ClassB bit to 1 in the frame’s FCtrl field. This can be done more efficiently if the end-
1666    device detects that it is moving by analyzing the beacon content. In that case, to avoid
1667    systematic uplink collisions, the end-device SHALL apply a random delay (as defined in
1668    Section 13.6) between having received the beacon and transmitting the uplink.
1669    During any Class A downlink, the Network Server MAY change the end-device’s ping-slot
1670    downlink frequency or data rate by sending a PingSlotChannelReq MAC command and
1671    receiving the corresponding PingSlotChannelAns.
1672    The end-device MAY change the periodicity of its ping slots at any time. To do so, it SHALL
1673    temporarily disable Class B operation (unset ClassB bit in its uplink frames) and send a
1674    PingSlotInfoReq to the Network Server. Once this command is acknowledged, the end-
1675    device MAY re-enable Class B operation with the new ping-slot periodicity.
1676    If no beacon has been received for a given period (as defined in Section 12.2),
1677    synchronization with the Network is lost. The end-device LoRaWAN layer SHALL stop
1678    setting the ClassB bit in all uplinks, which informs the Network Server that the end-device
1679    has disabled Class B mode.

1716   9.3 Downlink Ping Frames
1717   A downlink ping frame uses the same format as a Class A downlink frame but might follow a
1718   different channel frequency or data rate plan.

1721   multicast frames are sent to multiple end-devices. All end-devices of a multicast group SHALL
1722   share the same multicast address and associated encryption keys. A Class B-capable end-
1723   device SHALL support at least one multicast group and an end-device SHALL NOT transmit
1724   using a multicast address.
1725
1726   More precisely, inside a given end-device, a multicast group is defined by the following
1727   parameters called the multicast group context:
1728   1. A 4-octet network address of the multicast group, common to all end-devices of the group.
1729   2. The multicast group sessions keys (different for every multicast group, but all end-devices
1730      of a given multicast group have the same session keys).
1731   3. The multicast group downlink frame counter.

1739   9.3.1 Unicast downlink ping frame format

1740   The MAC payload of a unicast downlink ping uses the format defined in the Class A
1741   specification. The same frame counter is incremented, whether the downlink uses a Class B
1742   ping slot or a Class A downlink slot. A downlink ping is processed by the end-device in the
1743   same way as a Class A downlink, except for MAC commands and confirmed frames.
1744   A downlink ping SHALL NOT transport any MAC command. If an end-device receives a
1745   downlink ping containing a MAC command, either in the FOpts field (if FPort is either
1746   missing or >0) or in the FRMPayload field (if FPort=0), it SHALL silently discard the entire
1747   frame.
1748   In case a confirmed downlink ping frame is received, the end-device SHALL NOT answer later
1749   than a time period equal to CLASS_B_RESP_TIMEOUT * NbTrans + RECEIVE_DELAY2
1750   * (NbTrans-1) when the end-device sets its uplink ADR bit, and CLASS_B_RESP_TIMEOUT
1751   when the end-device unsets its uplink ADR bit. The default value of
1752   CLASS_B_RESP_TIMEOUT is 8s. It can be modified in [RP002], it SHALL not be smaller
1753   than RETRANSMIT_TIMEOUT plus the maximum time on air of the uplink frame.
1754

1755              Note: The purpose of this timeout is for the Network Server to know how
1756              long to wait for a response from the end-device, before it transmits
1757              another confirmed downlink. This ensures that the Network Server can
1758              process responses without any ambiguity: there may be only a single
1759              confirmed downlink ping pending an acknowledgement.
1760

1761   The uplink frame sent in response MAY be sent up to NbTrans times, but no retransmission
1762   SHALL occur after the timeout period. It is RECOMMENDED that the end-device transmits
1763   each copy of the uplink frame at a random time within CLASS_B_RESP_TIMEOUT.
1764   As this adds a timing requirement compared to responding to Class A downlinks, the end-
1765   device may not send an uplink frame within the timeout, for instance if it has a duty cycle
1766   limitation. When such an uplink frame is not sent, the end-device SHALL act as if the uplink
1767   frame with the ACK bit set was sent.
1768   After sending a confirmed downlink frame sent over pingslot, the network server SHALL NOT
1769   send any other confirmed downlink to the end-device until this timeout expires or an uplink
1770   frame is received from that end-device.
1771   After sending a Class A confirmed downlink, a network server SHALL NOT send any other
1772   confirmed downlink to the end-device until an uplink frame is received from that end-device.
1773

1774              Note: unconfirmed downlink frames sent over ping slots may be sent
1775              without a minimum delay between them.

1786   Before enabling Class B operation, the end-device SHOULD first synchronize with the network
1787   beacons to align its internal timing reference with the network.

1791   from the network gateways, presence of interference, etc.). In this event, the end-device
1792   SHOULD gradually widen its beacon and ping-slot reception windows to accommodate a
1793   possible drift of its internal clock.

1796                  a precision of ±10 ppm may drift by ±1.3 ms every beacon period.

1823   11 Class B Downlink Slot Timing

1824   11.1 Definitions
1825   To operate successfully in Class B, end-devices SHALL open reception slots at precise
1826   instants relative to the infrastructure beacon. This section defines the required timing.
1827   The interval between the start of two successive beacons is called the beacon period. The
1828   beacon frame transmission is aligned with the beginning of the BEACON_RESERVED
1829   interval. Each beacon is preceded by a BEACON_GUARD time interval, where no ping slot
1830   can be placed. The length of the BEACON_GUARD time interval corresponds to the time on
1831   air of the longest allowed frame. This is to ensure that a Class B downlink initiated during a
1832   ping slot just before the BEACON_GUARD time interval will always have time to finish without
1833   colliding with the beacon transmission. The usable time interval for a ping slot therefore spans
1834   from the end of the BEACON_RESERVED time interval to the beginning of the next
1835   BEACON_GUARD time interval.

2146   13.5 Beaconing Precise Timing
2147   A beacon SHALL be sent every 128s starting on January 6, 1980, 00:00:00 UTC (start of the
2148   GPS epoch) plus TBeaconDelay. Therefore, a beacon is sent at BT = k × 128 + TBeaconDelay
2149   ± TAccuracy seconds after the GPS epoch, where k is the smallest integer for which k × 128 >
2150   T and T = number of seconds since January 6, 1980 00:00:00 UTC (start of the GPS time).
        © 2020 LoRa Alliance®                    Page 70 of 90            The authors reserve the right to change
                                                                               specifications without notice.
                                                                LoRaWAN® L2 1.0.4 Specification



2151

2152              Note: T is GPS time and, unlike Unix time, it increases strictly
2153              monotonically and is not influenced by leap seconds.
2154
2155
2156   TBeaconDelay is 1.5 ms. It allows a slight transmit delay (1.5 ms) of the gateways required by
2157   their radio system to switch from receive to transmit mode.
2158   The variable TAccuracy denotes the timing precision guaranteed by the gateway. TAccuracy
2159   SHALL be provided by the gateway manufacturer with the set of operational conditions
2160   required to guarantee it. TAccuracy SHALL be less than or equal to the timing precision
2161   indicated by the Prec field of the beacon TAccuracy ≤ 10−6+Prec s.
2162   All gateways participating in the broadcast of the Class B beacon must be synchronized.
2163   Depending on the timing precision that can be guaranteed by the gateway, two possible
2164   modes of the Class B beacon transmission are possible.
2165          TAccuracy ≤ 1 µs: gateways tightly synchronized to GPS time.
2166   If the gateway transmissions can be synchronized to the GPS clock with an accuracy of better
2167   than 1 µs, the gateway MAY transmit the beacon every 128 s. The Prec field of the beacon
2168   is set to 0, indicating a timing accuracy of better than 1 µs for the listening end-devices.

2169          TAccuracy > 1 µs: gateways loosely synchronized to GPS time.
2170   If gateway transmissions can be synchronized to the GPS clock with an accuracy of better
2171   than 1 ms, but an accuracy of 1 µs cannot be guaranteed, the transmission of a Class B
2172   beacon SHALL be randomized. For each beacon, the gateway SHALL draw a random number
2173   P with a uniform distribution between 0 and 1. The gateway transmits the beacon if P <
2174   PBeacon. If P ≥ PBeacon, the gateway remains silent and does not transmit the beacon.

2175   The parameter PBeacon exists on the gateway and MAY be remotely set by the Network
2176   Server. The value of PBeacon SHALL be ≤ 0.5 (50%). Different gateways may use different
2177   values of the P Beacon parameter.
2178   The parameter P may be a pseudo-random number but, in this case, each gateway in the
2179   network SHALL use a different seed, resulting in a unique series of P values.
2180   If the Class B beacons of two or more loosely synchronized gateways reach the antenna of
2181   an end-device with equivalent power, the end-device may not be able to demodulate the
2182   beacon. The timing difference between the colliding beacons may be too great to be
2183   compensated correctly by the end-device’s demodulator. To avoid systematic beacon collision
2184   at the antenna of a stationary end-device, randomization must take place. Each loosely
2185   synchronized gateway randomly transmits the beacon no more than half of the time.
2186   Therefore, although beacon collisions do happen at the end-device’s antenna, they are not
2187   systematic, and the end-device can still demodulate the Class B beacon with sufficient
2188   probability to operate in Class B mode. The P Beacon parameter should be optimized by the
2189   network infrastructure based on the average number of gateways that local end-devices can
2190   receive. The denser the gateway population becomes, the higher the probability of beacon
2191   collision, so the lower the parameter should be. The optimal parameter value depends on too
2192   many network-driven factors and is beyond the scope of this specification.




        © 2020 LoRa Alliance®                  Page 71 of 90          The authors reserve the right to change
                                                                           specifications without notice.

2196   13.6 Network Downlink Route Update Requirements
2197   When the Network attempts to communicate with an end-device using a Class B downlink
2198   slot, it SHOULD transmit the downlink from the gateway closest to the end-device when the
2199   most recent uplink was received. Therefore, the Network Server SHOULD keep track of the
2200   approximate position of every Class B end-device.
2201   Whenever a Class B end-device moves and changes cells, it SHALL communicate with the
2202   Network Server in order to update its downlink route. This update is performed simply by
2203   sending a confirmed or unconfirmed uplink, possibly without applicative payload.
2204   The end-device can communicate in accordance with two basic strategies:
2205    Systematic periodic uplink: This is the simplest method as it does not require
2206     demodulation of the gateway-specific field of the beacon. It is applicable only to slowly
2207     moving or stationery end-devices. No requirements are imposed on such periodic uplinks.
2208    Uplink on cell change: The end-device can demodulate the optional gateway-specific field
2209     of the beacon. It detects that the ID of the gateway broadcasting the beacon it demodulates
2210     has changed and sends an uplink. In that case, the end-device SHALL respect a pseudo-
2211     random delay within the range of [0s:120s] between the beacon demodulation and the
2212     uplink transmission to ensure that the uplinks of multiple Class B end-devices entering or
2213     leaving a cell during the same beacon period will not systematically occur at the same time
2214     immediately after the beacon broadcast.
2215   Failure to report a cell change can result in a Class B downlink being temporarily not
2216   operational.

2217   14 Class B Unicast and Multicast Downlink Channel Frequencies
2218   The Class B downlink channel selection mechanism depends on the way the Class B beacon
2219   is broadcast.


2220   14.1 Single-Channel Beacon Transmission
2221   In certain regions (e.g., EU868), a beacon is transmitted on a single channel. In that case, all
2222   unicast and multicast Class B downlinks SHALL use a single frequency channel defined by
2223   the PingSlotChannelReq MAC command. The default frequency is defined in [RP002].


2224   14.2 Frequency-Hopping Beacon Transmission
2225   In certain regions (e.g., US902-928 or CN470-510), a Class B beacon SHALL be transmitted
2226   following a frequency-hopping pattern.
2227   In certain regions (e.g., CN470-510), the default Class B downlink channel is subject to the
2228   definition in the “Regional Parameters” document [RP002].
2229   In other regions with a hopping beacon, by default Class B ping slots SHALL use a channel
2230   that is a function of the Time field of the previous beacon (see Section 13.2) and the value of
2231   DevAddr.
                                                               BeaconTime
2232       Class B ping − slot channel = [DevAddr + floor (               )] modulo NbChannel ,
                                                              BeaconPeriod
2233   where
2234    BeaconTime is the 32-bit Time field of the current beacon period.
2235    BeaconPeriod is the length of the beacon period (defined as 128 s in the specification).
2236    floor designates rounding to the immediately lower integer value.
2237    DevAddr is the 32-bit network address of the end-device or multicast group.
2238    NbChannel is the number of channels over which the beacon is frequency hopping.
2239   Class B downlinks therefore hop across NbChannel channels (identical to the beacon
2240   transmit channels) in the ISM band, and all Class B end-devices are equally spread amongst
2241   the NbChannel downlink channels.
2242   If the PingSlotChannelReq command with a valid non-zero Frequency argument sets the

2247   NbChannel channels.

2249   proprietary dedicated frequency band for Class B downlinks if available, and to maintain as

2252   15 Continuously Listening End-Device (Class C)
2253   Class C mode is used for applications that have sufficient power available such that they do
2254   not need to minimize the time the radio receiver is active as they do in Class A or Class B
2255   applications.
2256   Class C-capable end-devices SHALL NOT enable Class B and Class C concurrently. Class A
2257   downlink, however, are always available after an end-device uplink.
2258   A Class C-enabled end-device listens as often as possible using a combination of channel/DR
2259   parameters referred to as RXC. The end-device SHALL listen on RXC when it is not (a)
2260   transmitting or (b) receiving on RX1 or (c) receiving on RX2, according to the Class A
2261   definition. To do so, it SHALL open a short window on RXC parameters between the end of
2262   the uplink transmission and the beginning of the RX1 reception window. It SHALL open
2263   another RXC window between the end of the RX1 window and the beginning of the RX2
2264   window, and it SHALL switch to RXC reception parameters as soon as the RX2 reception
2265   window is closed. This final RXC reception window SHALL remain open until the end-device
2266   begins to send another packet.
2267   If the end-device is in the process of demodulating a downlink using the RXC parameters
2268   when the RX1 or RX2 window should be opened, it SHALL stop the demodulation and switch
2269   to the RX1 or RX2 receive window. This applies even when the RXC and RX2 parameters are
2270   identical. The purpose of this rule is to achieve a clear separation between downlinks received
2271   during RX1 and RX2 windows (called Class A downlinks) and downlinks received during a
2272   Class C window (called Class C downlinks). The same frame counter is incremented, whether
2273   the downlink uses RX1/RX2 or RXC.
2274

2275              Note: In order to take advantage of the network-initiated downlink
2276              capabilities provided by Class C, the network needs relatively recent
2277              information of how to best contact the end-device. This information is
2278              provided to the network through any and all uplinks received from the
2279              end-device. For this reason it is important for Class C enabled end-
2280              devices to send regular uplinks which implicitly inform the network of the
2281              best way to contact it as well as providing the network a chance to send
2282              new MAC commands which may be required for proper end-device
2283              operation.
2284

2285   A Class C downlink SHALL NOT transport any MAC command. If an end-device receives a
2286   Class C downlink containing a MAC command, either in the FOpts field (if FPort is either
2287   missing or >0) or in the FRMPayload field (if FPort=0), it SHALL silently discard the entire
2288   frame.
2289   In case a Class C confirmed downlink is received, the end-device SHALL NOT answer later
2290   than a time period equal to CLASS_C_RESP_TIMEOUT * NbTrans + RECEIVE_DELAY2
2291   * (NbTrans-1) when the end-device sets its uplink ADR bit, and CLASS_C_RESP_TIMEOUT
2292   when the end-device unsets its uplink ADR bit. The default value of
2293   CLASS_C_RESP_TIMEOUT is 8s. It can be modified in [RP002], it SHALL not be smaller
2294   than RETRANSMIT_TIMEOUT plus the maximum time on air of the uplink frame.

2329   RXC window parameters
2330   The Class C mechanism may be used to receive unicast or multicast downlink frames:
2331    Unicast Class C downlinks are typically used for a command and control signal sent to a
2332     specific end-device with very low latency (e.g., single streetlight)
2333    Multicast Class C downlinks are used to broadcast the same downlink frame(s) to a group
2334     of end-devices. Typical applications include FUOTA and simultaneously controlling a group
2335     of end-evices such as streetlights.
2336   The RXC window parameters differ, depending on whether the Class C functionality is used
2337   to receive unicast or multicast downlinks:
2338    Unicast: The RXC parameters are identical to the RX2 parameters, and they use the same
2339     channel and data rate. Modifying the RX2 parameters using the appropriate MAC
2340     commands also modifies the RXC parameters.
2341    Multicast: The RXC parameters are provided by the application layer. All end-devices in the
2342     multicast group SHALL share the same RXC parameters. If the multicast RXC parameters
2343     are different from the end-device’s RX2 parameters, then the end-device is not able to listen
2344     simultaneously to multicast and unicast downlink. In that case, the decision whether the
2345     end-device should use unicast or multicast RXC parameters is application-specific. If the
2346     multicast RXC parameters provided by the application layer match the current RX2
2347     parameters of the end-device, then the end-device receives both unicast and multicast
2348     traffic during the RXC windows.


2349   15.1 Class C Multicast Downlinks
2350   Analogously to Class B, Class C end-devices can receive multicast downlink frames. The
2351   multicast address and associated network session key SHALL come from the Network Server,
2352   and the application session key SHALL come from the Application Server.
2353
2354   More precisely, inside a given end-device, a multicast group is defined by the following
2355   parameters called the multicast group context:
2356   1. A 4-octet network address of the multicast group, common to all end-devices of the group.
2357   2. A multicast group-specific session key, different for every multicast group; all end-devices
2358      of a given multicast group have the same session keys.
2359   3. A multicast group-specific downlink frame counter.
2360              Example: [TS005] provides an application layer mechanism to set up a
2361              multicast group over the air.
2362
2363   The following limitations apply for Class C multicast downlink frames:
2364    They SHALL NOT carry MAC commands in the FOpts field nor in the payload on port 0
2365     because a multicast downlink does not have the same authentication robustness as a
2366     unicast frame. The end-device SHALL discard any multicast frame carrying MAC
2367     commands.
2368    The ACK bits SHALL be 0 and the FType field SHALL carry the value for Unconfirmed
2369     Data Down. The end-device SHALL discard the multicast frame otherwise.
2370    Given that a Class C end-device keeps its receiver active most of the time, the FPending
2371     bit does not trigger a specific behavior of the end-device and SHALL NOT be used.
